# Класифікація відеотеки

## Використання

- `/admin?section=videos`: пошук за назвою, активністю, основною категорією, форматом і всіма вибраними тегами. «Без категорії», «Без формату» та «Потребує класифікації» допомагають завершити інвентаризацію.
- «Класифікація» біля ролика: категорія, формат, теги, необов’язкові WOW (0–100), case UUID, статус і примітка. Збереження оновлює класифікацію без перезавантаження адмінки.
- Виберіть декілька записів: «Класифікувати обрані» змінює лише явно вибрані поля; теги можна додати або прибрати, не замінюючи решту. Активувати/вимкнути та поточні дії зі звуком залишилися.
- `/admin?section=classification`: категорії, описи, порядок, активність; теги, групи, синоніми, кількість пов’язаних відео; об’єднання тегів усередині групи зі збереженням зв’язків і синонімів.
- Slug та UUID довідника постійні, їх зміну заборонено тригером. Унікальність назви/синонімів тегу перевіряється в межах групи. «Фрезерування» як технологія і як етап — різні дозволені виміри.
- Для щоденної роботи вимикайте ролик. Масове остаточне видалення записів потребує точного `ВИДАЛИТИ N` і показує назви. Воно видаляє класифікацію, зв’язки, відповідні video metadata та оригінальний звук видалених ID. Фізичні MP4 ніколи не видаляються цим інтерфейсом або RPC, навіть якщо URL спільний. Операції фізичного видалення немає: наявні зовнішні MP4 не належать цьому сховищу; майбутній R2 потребуватиме окремого підтвердження та перевірки посилань.

## Дані

| Таблиця                 | Призначення                                                                                                 |
| ----------------------- | ----------------------------------------------------------------------------------------------------------- |
| `video_categories`      | UUID, постійний slug, українська назва, опис, порядок, активність                                           |
| `video_content_formats` | Незалежні 7 форматів, UUID/slug/назва/порядок/активність                                                    |
| `video_tags`            | UUID/slug/назва, одна з 6 груп, синоніми, активність                                                        |
| `video_tag_aliases`     | Нормалізовані назви й синоніми; унікальна пара група/значення                                               |
| `video_classification`  | Один рядок на наявне `videos.id`; nullable категорія, формат, WOW, case UUID; статус і джерело класифікації |
| `video_tag_relations`   | Багато тегів на відео, унікальна пара video/tag; індекс для зворотного пошуку                               |

`case_id` зарезервований nullable UUID, а не посилання на вигадану таблицю кейсів. WOW не впливає на ефір. Основні URL, порядок, тривалість і активність залишаються в `videos`; наявні legacy metadata збережені для сумісності старого клієнта. Нова форма використовує нормалізований довідник як основну класифікацію.

TV не читає нові таблиці й продовжує відтворення без класифікації. Категорія не є вагою ротації. `taggedAirtime` рахує об’єднання UUID, а не суму перекривних тегів: подвійного підрахунку немає. Нового планувальника немає.

## Інвентаризація

`VIDEO_CLASSIFICATION_INVENTORY.csv` (UTF-8 BOM) та `content/video-classification-inventory.json` містять усі 25 фактичних ID, назви, порядок і запропоновану класифікацію. 14 класифіковано за явними відомостями назв; 11 потребують перевірки. Це не повний візуальний перегляд. «Без крові», WOW, до/після та невказані матеріали не вгадувалися. Усі WOW/case порожні.

`scripts/prepare-video-classification-inventory.mjs` читає приватний локальний знімок схеми й генерує guarded SQL ініціалізації. SQL відмовляється працювати, якщо змінився fingerprint відеотеки або класифікація вже заповнена. Повторно його не запускайте; виправляйте класифікації через адмінку. Публічний репозиторій не містить дампів Auth, секретів або локальних інвентарів інфраструктури.

## Міграція та безпека

`supabase/migrations/20261018175151_video_taxonomy.sql` створена офіційним Supabase CLI v2.121.0. Адитивна транзакція з lock timeout 5 секунд, FK, індексами, RLS і seed `ON CONFLICT(slug) DO NOTHING`: повторний запуск не перезаписує адміністративні правки. Міграція перевірена повторним застосуванням у staging. Це не універсальний засіб виправлення довільно зміненої схеми.

На всіх шести таблицях RLS: доступ authenticated лише за наявного `has_role(auth.uid(),'admin')`; anon не має SELECT/CRUD. `classify_videos`, `merge_video_tags`, `delete_video_records` — SECURITY INVOKER, без публічного виконання; додатково перевіряють роль. Auth-тригери та `has_role` не змінювалися. Bulk RPC транзакційні, обмежені 500 відео/100 тегами; помилковий FK чи значення відкочує всю операцію.

18 жовтня 2026 міграція та guarded ініціалізація виконані в оригінальному Lovable Cloud через офіційний query_database після перевірки фактичної схеми. Автоматичний `db push` попередніх міграцій не запускався; чужий migration history не підроблявся. Readback: 12 категорій, 7 форматів, 65 тегів, 25 класифікацій, 43 зв’язки, 14 classified/11 needs_classification, RLS 6/6, anon SELECT false, RPC invoker 3/3.

До/після збіглися контрольні суми всіх рядків `videos` (25, `1ef26b9529ddaa4238fd33f7165826e9`), `music_profiles`, `playback_settings`, реклами/її налаштувань, `user_roles`, `screens`; Auth 1 користувач і Storage 15 об’єктів збережені. Не виконувалося production-видалення чи вимкнення роликів для демонстрації тесту.

## Перевірки

- TypeScript; ESLint змінених TS/TSX; production build (чинна ціль Chromium 85).
- Vitest: 137 тестів / 23 файли, включно з фільтрами, nullable полями, AND тегами, унікальним airtime, bulk без перезапису полів, помилкою транзакції, створенням категорії, відмовою дублю синоніма та точним підтвердженням видалення.
- Launcher: обидві isolation-перевірки та 11 safety-тестів пройшли.
- `supabase/tests/video_taxonomy_integration.sql` виконано **тільки** на `smilestream-integration-test`, не на production. Транзакція з ROLLBACK: anon/користувач/admin; CRUD категорії; дубль синоніма; bulk теги; об’єднання; WOW і classified constraints; rollback FK; порожні поля/теги; вимкнення відео; підтвердження видалення/каскад; збереження іншого запису зі спільним URL. Фікстури не залишилися.
- Staging security advisor не показав нових taxonomy-проблем. Наявні попередження стосуються існуючих `assign_first_admin`/`has_role` ([0028](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable), [0029](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable)) та вимкненого [leaked password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) у staging. Ці налаштування Auth не змінювалися; це не висновок про відсутність будь-яких ризиків у всій системі.

Ручна перевірка на справжньому Samsung після релізу залишається потрібною: запуск, вибір профілю, декілька переходів, пульт, звук/ducking за наявності відео з оригінальним звуком. Production реклама наразі вимкнена й бібліотека реклами порожня: реальну рекламну вставку перевірити без зміни даних неможливо. Цей етап не додавав тестову рекламу.
